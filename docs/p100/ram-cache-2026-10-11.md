# RAMプロンプトキャッシュの適用と測定

2026-10-11、DESKTOP-HL7S64SのUnslothDesktopとLM Studioに、上限8,192 MiBのRAMプロンプトキャッシュを明示しました。モデルの量子化とF16 KVを維持しています。別の会話を処理した後に長い入力へ戻るケースで、キャッシュ無効時より最初の出力が速くなりました。

P100優先の通常の両GPU構成も、両アプリの9B/27Bで追加測定しました。入力長、通常コンテキスト、温度条件を含む結果は [P100通常構成の比較](ram-cache-primary-2026-10-11.md) を参照してください。以下の表はRTX退避構成の測定で、P100の結果とは分けて扱います。

## 適用内容

- Unslothの登録済み9B/27Bとファイル指定の別名8件に `cache_ram=8192`、`ctx_checkpoints=32`、`--cache-idle-slots` を保存しました。`configure_unsloth.py` で再適用できます。
- LM Studioの共通サービス設定に `ram_cache_mib=8192` を保存し、通常とRTX退避のどちらでもネイティブエンジンへ明示します。GPU構成が一致していてもRAM容量が異なる場合は、生成が終わった後に再ロードします。
- Unslothも共通サービスでロード後のRAM容量とチェックポイント数を照合します。設定が異なる既存モデルを使い続ける状態を修正しました。
- 通常のP100優先・3:2配分、78C以上または温度制限での退避、70C未満で120秒安定してから区切りで復帰する条件を維持しました。会話圧縮、Memorix、バックグラウンド要約も維持しています。

容量は必要な分だけ使う上限です。このPCはRAM 64 GiB、OSから見える容量は約63.12 GiBで、測定開始時の空きは約29 GiBでした。今回の入力は8 GiB以内で再利用できたため、上限をさらに増やした比較は行っていません。満杯時の退避や長時間運用も別の検証になります。

キャッシュ内容は各モデルプロセスに属します。アプリ間のモデル交換や温度切替でプロセスを再起動すると、RAMキャッシュは再作成されます。会話履歴と要約は従来の共有メモリに保存します。

## 変更前の状態

LM Studioの今回のカスタムllama.cppは、RAMキャッシュ8 GiBとチェックポイント32を初期値で使っていました。したがってLM Studioの測定は、今回初めて有効化した場合の改善率ではなく、意図的に無効化した場合との差です。

インストール済みUnslothの `core/inference/llama_cpp.py` は、Windowsで全層をGPUへ配置する条件下で、明示値がなければRAMキャッシュとチェックポイントを0にします。RTXとCPUを併用する27Bの退避構成はこの条件と異なります。今回の明示設定は、どちらの構成でも同じキャッシュ設定を使うためのものです。

## 測定方法

Ryzen 5 7600 / RTX 4070で、実際に各アプリがロードしたカスタムネイティブサーバーを測定しました。P100は測定中に使用せず、温度によるGPU切替を避けました。Unsloth 9Bは全層GPU、27Bは20層GPUとCPUの退避構成です。LM Studioも対応するRTX退避プロファイルを使いました。アプリのモデル選択、GGUFファイル、実プロセスのRAM引数を照合しています。

入力Aは4,846トークン、入力Bは先頭から異なる同程度の長さです。1回の測定は `A -> B -> A -> A` の順です。最初のAは新規入力、B後のAはRAMからの復元、最後のAは同じGPUスロットの再利用を調べます。無効時のB後のAは再処理4,846トークン、有効時は4,842トークンを再利用し、新たに処理したのは4トークンでした。比較する両設定のチェックポイント数は32に揃えました。

コンテキスト65,536、F16 KV、temperature 0、seed 1234、出力上限16を固定しました。測定リクエストだけthinkingを無効化しています。Aの期待出力は `42`、Bは `84` です。9Bは3回の中央値、27Bは1回の観測値です。27Bの再現性を統計的に評価した結果ではありません。

比較中は共通サービスとバックグラウンド要約を一時停止し、利用者の生成が待機中であることを確認してからロードしました。測定後にサービスと要約を再開しました。表はネイティブサーバーのリクエストから最初の表示テキストまでの時間で、DSHのツール実行や共有メモリ検索を含む全体時間ではありません。

## 結果

会話Bの後で会話Aへ戻った場合:

| アプリとモデル | RAM無効 | RAM 8 GiB | 待ち時間の短縮 | 回数 |
| --- | ---: | ---: | ---: | ---: |
| Unsloth 9B UD-Q4_K_XL | 1,454.63 ms | 158.54 ms | 89.10% | 3 |
| LM Studio 9B Q4_K_M | 1,474.27 ms | 137.53 ms | 90.67% | 3 |
| Unsloth 27B UD-Q4_K_XL | 12,317.35 ms | 1,107.32 ms | 91.01% | 1 |
| LM Studio 27B Q4_K_M | 18,763.19 ms | 1,167.91 ms | 93.78% | 1 |

新規入力Aの時間は次の通りです。RAMキャッシュで新規入力が速くなる結果は確認していません。

| アプリとモデル | RAM無効 | RAM 8 GiB |
| --- | ---: | ---: |
| Unsloth 9B | 1,482.79 ms | 1,549.64 ms |
| LM Studio 9B | 1,472.39 ms | 1,500.94 ms |
| Unsloth 27B | 12,406.45 ms | 12,264.17 ms |
| LM Studio 27B | 18,490.89 ms | 18,477.02 ms |

さらに、Unslothの従来のWindows全層GPU設定に相当するRAM 0 / チェックポイント0との比較も行いました。9Bの新規入力は初回のウォームアップを除く2回で約1.38-1.39秒、有効化後は約1.54-1.55秒でした。チェックポイント作成を含むため新規入力には負担があります。一方、同じ会話を直後に繰り返す場合も、チェックポイント0では約1.39秒の再処理、32では約41 msの再利用になりました。

比較表の64応答すべてで期待出力、終了理由 `stop`、出力SHA-256が一致しました。モデルファイル、GPU層数、KV型を変更していません。ただし短い固定回答の比較であり、一般的な回答品質や長時間の生成速度を評価したものではありません。履歴の先頭や共有情報が変わると、再利用できるトークン数も変わります。

集計値は [JSON](ram-cache-2026-10-11.json)、元の測定値はローカルの `outputs/ram-cache/*.json`、再測定用スクリプトは `scripts/p100/benchmark_ram_cache.py` にあります。プロンプトキャッシュの仕組みは [llama.cppの導入PR](https://github.com/ggml-org/llama.cpp/pull/16391) を参照できます。

## 再適用と検証

Unslothの対象モデルに適用する例:

```powershell
& "$env:USERPROFILE\.unsloth\studio\unsloth_studio\Scripts\python.exe" -X utf8 scripts/p100/configure_unsloth.py --runtime release/p100-unsloth-thermal-20261009 --model "unsloth/Qwen3.8-27B-GGUF" --cache-ram 8192 --ctx-checkpoints 32
```

LM Studioは `~/.llama.cpp/desktop/config.json` の `ram_cache_mib` を使用します。共通サービスは設定を起動時に読みます。変更後は生成の終了を待ち、管理スクリプトで共通サービスを再起動してください。モデルは待機時に設定を照合します。

単一アプリを測定する例。生成中のモデルがあればスクリプトは拒否します。既定ではRTX退避プロファイルへモデルをロードします。`--gpu-profile primary` で通常構成を選べます。どちらも共通サービスと要約が動いていない検証時間に使います。P100測定ではロード前と各入力前に冷却を待ち、生成前の78C以上・熱制限を拒否し、測定中の温度境界や熱制限を検出した結果も不採用にします。冷却後と各入力前に生成・モデル・プロセスを再確認します。

```powershell
& "$env:USERPROFILE\.unsloth\studio\unsloth_studio\Scripts\python.exe" -X utf8 scripts/p100/benchmark_ram_cache.py --app unsloth --model unsloth/Qwen3.8-27B-GGUF --cache-mib 0 --checkpoints 32 --rounds 1 --output outputs/ram-cache/unsloth-27b-0-32.json
& "$env:USERPROFILE\.unsloth\studio\unsloth_studio\Scripts\python.exe" -X utf8 scripts/p100/benchmark_ram_cache.py --app unsloth --model unsloth/Qwen3.8-27B-GGUF --cache-mib 8192 --checkpoints 32 --rounds 1 --output outputs/ram-cache/unsloth-27b-8192.json
```

今回の検証コマンド:

- コミット対象のファイルだけを別ディレクトリに展開し、`python -X utf8 -m unittest test_configure_unsloth test_desktop_service test_thermal_unsloth test_install_desktop_service test_benchmark_ram_cache` を実行: 72件成功。温度境界や比較中に新しい生成が入る場合の拒否も含みます。
- `node --test scripts/p100/test_lmstudio_cache.cjs`: 通常・退避構成の引数を調べる1件成功。
- `node --check scripts/p100/lmstudio_bridge.mjs`、`git diff --check`: 成功。
- Ruff: 変更したPythonファイルで成功。既存のバックエンドimportを含む `configure_unsloth.py` のみ `--ignore E402` を使用。
- Ty: `benchmark_ram_cache.py`、`desktop_service.py`、`install_desktop_service.py`、`test_configure_unsloth.py` で成功。

実際に使う共通サービスの7補助ファイルを更新し、インストール記録、配置先、リポジトリのSHA-256を照合しました。Unslothの配布先は既存の `release/p100-unsloth-thermal-20261009` を維持し、設定スクリプトとレシピハッシュを更新しています。C++/CUDAバイナリは再ビルドしていません。

再開後の共通APIでUnsloth 27B、LM Studio 27B、LM Studio 9Bに順にリクエストし、すべてHTTP 200、期待回答 `42`、終了理由 `stop` を確認しました。3回ともネイティブ引数は `--cache-ram 8192` で、Unslothは実行情報の `requested_cache_ram=8192` と `requested_ctx_checkpoints=32` も一致しました。詳細は [配置・API確認記録](ram-cache-live-2026-10-11.json) に保存しています。

このAPI確認時の共通サービスPIDは25396、その子のUnsloth温度監視PIDは36540でした。バックグラウンド要約と共有メモリは有効です。LM Studioは検証前と同じ9Bを最後に選択しました。冷却後に `matched-primary` / `CUDA1,CUDA0` へ戻ることを確認し、その後の要約負荷で再び退避条件に達したため、この記録の最終スナップショットは `matched-fallback` / `CUDA0` です。この状態でもRAM 8 GiB、チェックポイント32、F16 KVが維持されています。

今回のコミットはRAM設定、設定スクリプトの前提修正、測定と関連テスト・記録に限定します。稼働先の補助ファイルとハッシュ記録には、作業ツリーに残る別作業のDSH診断や復帰温度69Cの変更も含まれます。配置先のハッシュは作業ツリーとの一致を示し、コミット内の全ファイルと一致する意味ではありません。コミット対象だけの検証は上記の72件とNodeテストで行いました。

## P100測定後の再開

P100通常構成の追加測定後、2026-10-11T05:18:13.444714+00:00に共通サービスPID 47628、温度監視子PID 47984の生存とAPI状態 `matched-fallback` を確認しました。検証前に選択されていた `qwen/qwen3.5-9b` へ戻し、実プロセスのRAM 8 GiB、チェックポイント32、F16 KVを再照合しました。Unslothの保存済み8設定と、配置した7補助ファイルのハッシュ一致も確認しました。保存設定の退避78C、復帰69C以下・安定120秒、共有メモリとバックグラウンド要約の有効設定を維持しています。これは再開状態と設定の確認であり、新しい要約完了の性能測定ではありません。詳細は [配置・API確認記録](ram-cache-live-2026-10-11.json) の `primary_validation_after_restore` を参照してください。
